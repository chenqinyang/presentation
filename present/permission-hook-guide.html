03 /

Use detail only where you need it.

One hook provides the full screen’s permission interface. A dedicated result variable is needed only for an action with detailed feedback.

CustomerDetails.tsxProposed public API
const { can, getPermission } = usePermissions([
  "customers.financials.read",
  "customers.contact.update",
  "customers.export",
]);

const update = getPermission(
  "customers.contact.update"
);

return (
  <>
    {can("customers.financials.read") && (
      <FinancialDetails />
    )}

    <button disabled={!update.allowed}>
      Update contact
    </button>

    {update.status === "loading" && (
      <p>Checking permission…</p>
    )}
    {update.status === "denied" && (
      <p>{permissionMessage(update.reason)}</p>
    )}
    {update.status === "error" && (
      <p>Permission check failed. Try again.</p>
    )}

    <button disabled={!can("customers.export")}>
      Export customer
    </button>
  </>
);

Keep identity inside the Controller

Journey engineers pass business action IDs. The Host adapter supplies the current staff ID and selected role. A screen cannot switch identity by passing a different staff ID.

Subscribe once; read synchronously

The hook declares actions, deduplicates requests, and subscribes to store changes. can() and getPermission() never return promises or fetch during render. Both read the same snapshot for that render.

Use action-specific status

One permission can be allowed while another is loading or has failed. An optional screen-level loading summary must not replace each action’s own result.

Normalize safe reason codes

Map Host responses to stable codes such as STAFF_NOT_GRANTED or CHECK_FAILED. Translate codes into helpful messages; do not display raw backend errors.

Controller contractTypeScript prevents contradictory states
type PermissionResult =
  | { status: "allowed"; allowed: true }
  | {
      status: "loading" | "denied" | "error";
      allowed: false;
      reason?: string;
    };

type PermissionApi = {
  can(action: ActionId): boolean;
  getPermission(action: ActionId): PermissionResult;
};

status is the source of truth. Derive allowed from it; never update these independently. For an external Controller store, React’s useSyncExternalStore can provide subscriptions, with stable cached snapshots. A Context provider is also valid.

Permission policy · illustrative JSON
  1. Validate the selected role
    The server resolves the signed-in employee, verifies role assignment, and establishes the authorized tenant context. An employee-specific grant does not grant the role itself.
  2. Find the exact action
    Evaluate only the active role’s configuration. Missing or unknown actions are denied. Do not merge permissions from all assigned roles.
  3. Apply matching denials first
    If the authenticated staff ID appears in deny.staffIds, deny the action even when allow.allStaff is true.
  4. Evaluate grants
    Allow if allow.allStaff is true or the employee is included in allow.staffIds. Otherwise deny. Use exact string IDs.

    
“All staff” is scoped to this selected role and tenant. It does not mean every employee in the organization. These are action entitlements; record ownership, permitted fields, and workflow conditions remain additional backend checks.

05 /
Keep decisions attached to their context.
A role switch must immediately stop the Journey from using the previous role’s permissions. A late response must never restore an old grant.

    
  1. 01 / SELECT
    Validate a new role
    The Host requests the change. The backend validates membership and rotates the authorization context.
  2. 02 / INVALIDATE
    Return loading / false
    Discard old decision snapshots and sensitive data. Disable protected interactions during the transition.
  3. 03 / REFRESH
    Check the new context
    Batch the screen’s action IDs. Ignore responses whose context or request generation is superseded.
  4. 04 / NOTIFY
    Rerender subscribers
    Publish fresh per-action results. Recheck routes and remove content the new role cannot access.

    
Cache with identity and policy scope
Partition by Host/tenant, authenticated employee, active-role context, and action. Track policy revision or expiry and invalidate on changes. Add resource identity when checks become resource-specific.
Do not create checks during render
Declare needed actions in the hook or preload them at Journey entry. Undeclared or unknown actions must not silently allow access. A valid snapshot is required before can() returns true.
