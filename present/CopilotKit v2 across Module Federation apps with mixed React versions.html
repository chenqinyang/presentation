One CopilotKit v2 brain, three React versions

Host UI (React 19.3.1), Content UI (19.2.8) and AI Panel UI (19.2.9) can share one CopilotKit session without aligning React, if the shared part contains no React at all.

Recommendation. Put a small framework-agnostic bridge in the Host. Content UI registers context, tools and components into it. The AI Panel reads from it and talks to the agent. Each app keeps its own React and its own thin hooks. Components cross the boundary as mount(el, props) functions, never as React components.

Why the versions matter

CopilotKit’s React layer is built on React context and hooks. Both are tied to the React instance that created them. When three bundles each carry their own React and their own @copilotkit/react-core, you get three independent providers: the Content UI registers into one store and the AI Panel reads from another, so it sees nothing.

Two separate issues follow:

  • Shared state. Registrations and the agent must live in exactly one object that all three apps can reach.
  • Cross-tree rendering. A tool UI registered by Content UI is displayed inside the AI Panel. If the panel’s React renders a function component that calls hooks from Content’s React copy, the hook runs without a dispatcher and throws “Invalid hook call”. Plain React elements are compatible across 19.x, but components with hooks are not.

Architecture for option B

Because the bridge has no React import, it never touches a hook or a context. Only plain objects, functions and JSON-serializable values cross the boundary.

Implementation

1. The bridge package

Publish it as an internal package (@acme/copilot-bridge) with no dependency on React. The Host creates it once and exposes it through Module Federation. Check the CopilotKit v2 API names below against the version you installed: the registration calls on the core object may be named differently.

copilot-bridge/src/index.ts
import { CopilotKitCore } from "@copilotkit/core"; // framework-agnostic core

type Scope = string;
type Off = () => void;

export interface MountableComponent {
  name: string;
  schema: unknown;                       // JSON Schema, not a zod instance
  mount(el: HTMLElement, props: any): () => void; // returns unmount
}

class Bridge {
  core = new CopilotKitCore({ runtimeUrl: "/api/copilotkit" });
  private offs = new Map<Scope, Set<Off>>();
  components = new Map<string, MountableComponent>();
  private listeners = new Set<() => void>();

  private track(scope: Scope, off: Off): Off {
    (this.offs.get(scope) ?? this.offs.set(scope, new Set()).get(scope)!).add(off);
    return () => { off(); this.offs.get(scope)?.delete(off); };
  }
  registerContext(scope: Scope, ctx: { description: string; value: unknown }) {
    return this.track(scope, this.core.addContext(ctx));      // verify name
  }
  registerTool(scope: Scope, tool: { name: string; description: string;
      parameters: unknown; handler(args: any): Promise<unknown> | unknown }) {
    return this.track(scope, this.core.addTool(tool));         // verify name
  }
  registerComponent(scope: Scope, c: MountableComponent) {
    this.components.set(c.name, c); this.emit();
    return this.track(scope, () => { this.components.delete(c.name); this.emit(); });
  }
  clearScope(scope: Scope) { this.offs.get(scope)?.forEach(o => o()); this.offs.delete(scope); }
  getAgent(id = "default") { return this.core.getAgent(id); }  // verify name
  subscribe(fn: () => void) { this.listeners.add(fn); return () => this.listeners.delete(fn); }
  private emit() { this.listeners.forEach(f => f()); }
}

// one instance per page, even if the module were loaded twice
const KEY = Symbol.for("acme.copilot.bridge");
export const bridge: Bridge =
  ((globalThis as any)[KEY] ??= new Bridge());

The Symbol.for guard is a safety net: if Module Federation ever loads the package twice, everyone still gets the same instance.

2. Module Federation: share the bridge, not React

rsbuild.config.ts (host and every remote)
import { defineConfig } from "@rsbuild/core";
import { pluginReact } from "@rsbuild/plugin-react";
import { pluginModuleFederation } from "@module-federation/rsbuild-plugin";

export default defineConfig({
  plugins: [
    pluginReact(),
    pluginModuleFederation({
      name: "content_ui",                 // host: name + remotes; remote: name + exposes
      exposes: { "./mount": "./src/mount.tsx" },
      shared: {
        // shared, singleton, React-free
        "@acme/copilot-bridge": { singleton: true, requiredVersion: "^1.0.0" },
        "@copilotkit/core":     { singleton: true, requiredVersion: "^2.0.0" },

        // do NOT list react / react-dom / @copilotkit/react-core here.
        // each app bundles its own copy, so 19.2.8 / 19.2.9 / 19.3.1 coexist.
      },
    }),
  ],
});

Rsbuild’s plugin is the Module Federation 2.0 runtime, so the shared options behave as described here. By default the plugin shares nothing, which is what you want for React in option B. For option A, you would add react, react-dom and @copilotkit/react-core with singleton: true and a range such as ^19.2.0.

If the Host should still share React with itself only, leave it out of shared too. Each remote mounts with its own createRoot, which is already the normal pattern for remotes that export a mount function.

3. Content UI: register through a thin hook

content-ui/src/useBridge.ts
import { useEffect } from "react";               // Content’s own React
import { bridge } from "@acme/copilot-bridge";

export function useBridgeContext(scope: string, description: string, value: unknown) {
  useEffect(() => bridge.registerContext(scope, { description, value }),
            [scope, description, JSON.stringify(value)]);
}
export function useBridgeTool(scope: string, tool: Parameters<typeof bridge.registerTool>[1]) {
  useEffect(() => bridge.registerTool(scope, tool), [scope, tool.name]);
}

The returned function is the cleanup, so leaving a page removes its context and tools automatically. The Host also calls bridge.clearScope(oldScope) on menu change as a backstop.

4. Components: export mount, not a React component

content-ui/src/components/ChartCard.tsx
import { createRoot } from "react-dom/client";   // Content’s own react-dom

export const chartCard: MountableComponent = {
  name: "ChartCard",
  schema: { type: "object", properties: { series: { type: "array" } } },
  mount(el, props) {
    const root = createRoot(el);
    root.render(<ChartCard {...props} />);       // runs entirely in React 19.2.8
    return () => root.unmount();
  },
};
// in the page: useEffect(() => bridge.registerComponent(scope, chartCard), []);

5. AI Panel: read from the agent and host mounted components

ai-panel/src/MountedComponent.tsx
import { useEffect, useRef } from "react";        // Panel’s own React
import { bridge } from "@acme/copilot-bridge";

export function MountedComponent({ name, props }: { name: string; props: any }) {
  const ref = useRef<HTMLDivElement>(null);
  useEffect(() => {
    const c = bridge.components.get(name);
    if (!c || !ref.current) return;
    return c.mount(ref.current, props);            // cleanup = unmount
  }, [name, JSON.stringify(props)]);
  return <div ref={ref} />;
}

For the chat itself, use CopilotKit’s React hooks inside the AI Panel only. They run against the panel’s own React. If the v2 provider can accept an existing core, pass bridge.core to it. If it creates its own core, let the panel own the provider and have the bridge forward registrations to that core, buffering anything registered before the panel is ready.

Menu switching

  1. Host sets scope = menuItemId and loads that Content UI remote.
  2. Content UI mounts, and its hooks register context, tools and components under that scope.
  3. Host menu change unmounts the old remote. Cleanups fire, then Host calls clearScope(oldScope).
  4. AI Panel never unmounts. It sees the registry change through the bridge and the next agent run uses the new tools and context.
Race to guard against: if the old tool is still registered when the new page mounts, two tools can share a name. Give tools unique names or prefix them with the scope, and clear the old scope before loading the new remote.

Rules that keep it working

  • Nothing React crosses the bridge. No elements, hooks, refs, contexts or components. Only plain data, functions and mount().
  • Schemas as JSON Schema. If apps use different zod versions, pass JSON Schema over the bridge so version differences don’t matter.
  • Context values must serialize. The agent reads JSON, so keep functions and class instances out.
  • Version the contract. Bump the bridge’s major version when the registry shape changes, and use requiredVersion so a mismatch fails loudly.
  • Styles. Components mounted in the panel bring their own CSS. Use CSS modules or a scoped prefix so they don’t leak into the chat UI.
  • Test pair. Add one end-to-end test: switch menu, assert tools change, trigger a tool that renders a component, assert it unmounts cleanly.

Treat the code above as a starting skeleton. The shape of the design is what matters: one React-free singleton, per-app React adapters, scoped registration and mount() for components.
